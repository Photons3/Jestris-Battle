# Design: Duel stats (PPS, APM, VS and a results breakdown)

## Context
The duel centre column shows TIME, the match target, COMBO and SENT. Versus players compare play with PPS (pieces per second), APM (attack per minute) and VS score, and the result screen shows only the title and one reason line.

This adds stat counters to `Game`, sends them to the opponent inside the existing snapshot, shows live PPS and APM in the centre scoreboard, and adds a stats table to the duel result screen. Online duels and the practice bot both build snapshots with `snapshotOf`, so both get the stats.

## Goals and non-goals
- **Goals:**
  - Running totals in `Game`: pieces, attack, garbage cleared, garbage cancelled, tetrises, T-spins and highest combo.
  - Live `PPS` and `APM` rows in the duel centre scoreboard, for both players.
  - A table on the result screen comparing both players on PPS, APM, VS, Sent, Cancelled, Tetrises, T-spins and Max combo.
- **Non-goals:**
  - Showing stats in solo modes. The counters run there, but nothing displays them.
  - Back-to-back and perfect-clear counts.
  - Any change to the Go server.
  - Reading the old `SNAP` format.
  - Saving stats or keeping match history.

## Definitions
These follow TETR.IO, where the terms come from.

| Stat | Definition |
|---|---|
| PPS | pieces locked ÷ seconds played |
| APM | attack ÷ minutes played |
| VS | (attack + garbage cleared) ÷ seconds played × 100 |
| Attack | all garbage generated by clears, `awardAttack(award_, combo_)`, **including** the part that cancelled incoming garbage. SENT counts only what reached the opponent. |
| Garbage cleared | cleared rows that were garbage rows: any row with a `Garbage` or `Bomb` cell |
| Cancelled | incoming lines removed by our clears before they rose |
| Tetris | a lock that completes exactly 4 full rows (`award_.lines == 4`); bomb rows in the same lock don't matter |
| T-spin | a lock whose award has `spin != Spin::None`: full or mini, with or without lines |
| Max combo | highest `Game::combo()` reached, the number the COMBO row shows |

**Seconds played** is the time in the `Playing` phase: from the end of the countdown until the clock reaches 0:00 or the match ends. The KO flash counts as time played.

## 1. Counters (`core/game.{hpp,cpp}`)

```cpp
// Running totals for match stats. They survive resetBoard(); a new Game starts them at zero.
struct GameStats {
    int pieces = 0;          // pieces locked (holds don't count)
    int attack = 0;          // garbage generated by clears, before cancelling
    int garbageCleared = 0;  // cleared rows that were garbage rows
    int cancelled = 0;       // incoming lines cancelled by our clears
    int tetrises = 0;        // locks that completed exactly 4 full rows
    int tSpins = 0;          // locks that were T-spins, full or mini, with or without lines
    int maxCombo = 0;        // highest combo() reached
    friend bool operator==(const GameStats&, const GameStats&) = default;
};
```

`Game` gets a `GameStats stats_` member and a public `const GameStats& stats() const`.

- **`lockPiece()`**, after the lock-out check:
  - `++stats_.pieces`. The piece that locks out doesn't count.
  - Once `award_` is built: if `award_.lines == 4`, `++tetrises`; if `award_.spin != Spin::None`, `++tSpins`.
  - `stats_.maxCombo = std::max(stats_.maxCombo, combo_)`.
- **`finishClear()`**:
  - Before `removeRows`, `stats_.garbageCleared` goes up by the number of rows in `clearingRows_` that hold a `Garbage` or `Bomb` cell.
  - `stats_.attack += attack` (the existing local, before cancelling).
  - `stats_.cancelled += cancelled` (the existing local).
- A T-spin that clears nothing returns from `lockPiece()` early and sends nothing, so it adds to `pieces` and `tSpins` only.
- **Lifetime:**
  - `resetBoard()` (a duel KO) leaves `stats_` alone, the same way it keeps score and lines.
  - Each match builds a new `Game`, so its stats start at zero.

## 2. Protocol (`net/protocol.{hpp,cpp}`)

- `Snapshot` gains `GameStats stats{};`. `snapshotOf` copies `game.stats()` into it.
- The wire format puts the seven stats between `pending` and the hold, in struct order:

  ```
  SNAP <score> <lines> <pending> <pieces> <attack> <garbageCleared> <cancelled> <tetrises> <tSpins> <maxCombo> <hold> <next> <cells>
  ```

- The decoder needs exactly 13 arguments, and each stat must be a non-negative integer. Anything else, including the current 6-argument form, decodes to `nullopt`.
- The server relays `SNAP` without reading it, so `server/` does not change.
- **Accepted risk:** a tab still running a cached old build can't read the new snapshots, and the new build can't read the old ones. Each player then sees an empty opponent board. The server already sends `index.html` with `no-cache` and versions the script, so a reload fixes it.
- Snapshots are still sent only when they change. A lock changes the board anyway, so traffic stays about the same.

## 3. Time and rates (`app/duel.{hpp,cpp}`)

- `int DuelSession::playedMs() const { return kMatchMs - matchClockMs_; }`
  - The match clock runs only while `Playing`, stops at 0, and keeps its value in `Result` after an early KO finish. So this works with no new state.
  - It is 0 during the countdown.
  - The display clock always counts down from 2:00, even when the server's `-match` is shorter, so this still measures the time actually played.
- Pure rate function:

  ```cpp
  struct MatchRates {
      double pps = 0.0;
      double apm = 0.0;
      double vs = 0.0;
  };
  // PPS, APM and VS for `stats` over `playedMs` of play. All zero when playedMs <= 0.
  MatchRates ratesOf(const GameStats& stats, int playedMs);
  ```

- **Mine:** `ratesOf(game()->stats(), playedMs())`. **Theirs:** `ratesOf(opponent().stats, playedMs())`.
  - The opponent's rates use our clock. The two clocks differ by about one network delay. Sending the opponent's clock instead would change every snapshot and defeat the "only send when changed" check.
- **Final numbers:** on the result screen, the opponent's figures come from their last snapshot, which can be about 100 ms behind their last lock. This is accepted. If the opponent leaves, their last known numbers are shown.

## 4. Live scoreboard (`app/render.cpp`, `drawScoreboard`)

- Two rows go under `SENT`: `PPS` (`%.2f : %.2f`) and `APM` (`%.1f : %.1f`). They use the same label and value sizes and colours as `SENT`.
- The spacing after `COMBO`, `SENT` and `PPS` is `3.0f` cells (`COMBO` currently uses `3.5f`). The APM value then ends about 19.1 rows below the well top, inside the 20 visible rows.
- If a value is wider than the 7-cell centre column, its font size is scaled down to fit. A `drawCenteredFit` helper measures with `CalcTextSizeA` first.
- The rows show zeros during the countdown. They keep their final values in `Result`, behind the menu.

## 5. Result breakdown (`app/duel.{hpp,cpp}`, `app/render.cpp`)

- Pure formatter next to `resultReasonText`:

  ```cpp
  struct StatRow {
      std::string label;
      std::string mine;
      std::string theirs;
      friend bool operator==(const StatRow&, const StatRow&) = default;
  };
  // The result screen's stats table, ours on the left. Empty outside Result.
  std::vector<StatRow> resultStatRows(const DuelSession& duel);
  ```

  | Row | Source | Format |
  |---|---|---|
  | PPS | `ratesOf(...).pps` | `%.2f` |
  | APM | `ratesOf(...).apm` | `%.1f` |
  | VS | `ratesOf(...).vs` | `%.1f` |
  | Sent | `sentMine()` / `sentTheirs()` (the server's totals from `OVER`) | integer |
  | Cancelled | `stats.cancelled` | integer |
  | Tetrises | `stats.tetrises` | integer |
  | T-spins | `stats.tSpins` | integer |
  | Max combo | `stats.maxCombo` | integer, or `-` when 0 (like the COMBO row) |

- `drawDuelResult` draws a three-column ImGui table (blank header, `You`, the opponent's name or `Them`) between the reason line and the Rematch/Leave controls, for every outcome including "opponent left".
- "VS" appears only in this table. The scoreboard has no other "VS" label, and the countdown's VS line is gone by then.

## Testing
Doctest, written first.

- **`game_test.cpp`: counters**
  - `pieces` counts every lock. Hold doesn't add one, and the lock-out piece doesn't either.
  - A tetris adds one to `tetrises`. A double doesn't.
  - Queue 3 garbage lines, then clear a tetris: `attack == 4`, `cancelled == 3`, `takeOutgoingAttack() == 1`.
  - `garbageCleared` counts bomb rows set off, and it counts a garbage row completed by a piece.
  - A T-spin double and a zero-line T-spin each add one to `tSpins`. A T dropped in without spinning doesn't.
  - `maxCombo` keeps its peak after the combo breaks.
  - `resetBoard()` keeps the stats.
- **`protocol_test.cpp`: wire format**
  - A `Snapshot` with non-zero stats survives encode and then decode unchanged.
  - The existing `SNAP` string checks are updated to the 13-argument form.
  - The 6-argument form decodes to `nullopt`, and so does a negative or non-numeric stat.
- **`duel_test.cpp`: duel flow**
  - `playedMs()` is 0 during the countdown, grows while `Playing`, and stays fixed in `Result`.
  - The stats in a received `SNAP` show up in `opponent().stats`.
  - A sent `SNAP` carries the local game's stats.
  - `ratesOf` returns all zeros at 0 ms. A worked example: 60 pieces, 30 attack and 10 garbage cleared over 60 000 ms gives PPS 1.0, APM 30.0, VS ≈ 66.67.
  - `resultStatRows` is empty outside `Result`. In `Result` it has the 8 labels in order and the right formatting, and shows `-` for a max combo of 0.
- **`ui_test.cpp`:** draw the result phase with the table, headless, so the ImGui table calls run without asserting.
- **`server/hub_test.go`:** no change. It already relays an arbitrary `SNAP`.
- **Manual:**
  - Build for the web and play the practice bot and a two-tab duel.
  - Screenshot the live scoreboard and confirm the PPS and APM rows fit.
  - Screenshot the result table.
